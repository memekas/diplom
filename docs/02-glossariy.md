# 02 — Глоссарий предметной области и системы

## Введение

Глоссарий фиксирует единый словарь проекта «Padel Tournaments»: термины предметной
области (падел и его форматы) и технические понятия системы. Цель — устранить
разночтения между главами проектной документации и между документом и кодом: один и тот
же объект всюду называется одинаково.

**Как пользоваться.** Технические идентификаторы (имена моделей данных, полей, функций,
значений-перечислений) приводятся **латиницей — точно как в исходном коде** (`Tournament`,
`scoringMode`, `recordResult`, `"in_progress"`), а рядом даётся русское пояснение. Это
позволяет читать документацию и код без перевода терминов в голове. Перечисления (роли,
статусы, форматы, режимы) в базе данных SQLite хранятся как обычные строки и проверяются
на уровне приложения (Zod-union / TypeScript-union), поэтому их значения тоже даны
латиницей в кавычках.

Разделы: предметная область падела → форматы турниров → подсчёт результатов → системные
(архитектурные) термины → сущности модели данных. Детали структуры данных вынесены в
[модель данных](04-model-dannyh.md); подробности форматов и подсчёта — в
[форматы и алгоритмы](05-formaty-i-algoritmy.md) и [подсчёт и standings](06-podschyot-i-standings.md).

## 1. Предметная область (падел)

Падел — командный ракеточный спорт. В платформе моделируются игроки, их объединение в
пары и проведение турниров между ними.

| Термин | Определение |
|--------|-------------|
| **Падел** | Командный ракеточный вид спорта; в классическом матче за каждую сторону играют **два игрока** (пара). Предметная основа платформы; для системы важны прежде всего сущности «игрок», «пара» и «турнирная сетка». |
| **Корт** | Игровая площадка для матча. В round-based-форматах матч раунда привязан к конкретному корту через поле `courtNumber` (номер корта), что позволяет проводить несколько матчей раунда параллельно. |
| **Сторона корта** (`courtSide`) | Предпочтительная позиция игрока в паре: `left` (левая), `right` (правая) или `either` (любая). Хранится в профиле игрока, по умолчанию `either`. Не запрашивается при регистрации — задаётся позднее в личном кабинете. Справочно-описательное поле, на алгоритмы посева/ротации не влияет. |
| **Игрок** (`User`) | Зарегистрированный пользователь-участник. Идентифицируется уникальным никнеймом (`nickname`) и email. Имеет обязательный уровень игры (`skillLevel`); участвует в турнирах одиночно или в составе пары. |
| **Никнейм** (`nickname`) | Обязательный уникальный человекочитаемый идентификатор игрока (`@@unique`, точное регистрозависимое совпадение). Используется, в частности, для поиска партнёра при записи парой. |
| **Пара** (`Pair`) | Команда из двух игроков, зарегистрированная в конкретном турнире: `player1` — записывающий игрок (инициатор), `player2` — выбранный партнёр. Базовая соревновательная единица парных форматов (playoff, парный round_robin). |
| **Уровень игры** (`skillLevel`) | Квалификация игрока, одно из **пяти** фиксированных значений. Турнир также имеет уровень (`level`); при записи требуется строгое равенство уровня игрока и турнира. |
| **Сет** (`SetScore`) | Часть матча в режиме подсчёта по сетам. Содержит число геймов, выигранных каждой стороной (`gamesPair1`, `gamesPair2`), и номер сета в матче (`setNumber`). |
| **Гейм** | Минимальная учётная единица счёта внутри сета. В режиме `sets` победитель сета определяется по числу выигранных геймов. Очки внутри гейма (15/30/40) система не ведёт. |
| **Очко** (`points`) | Единица счёта в режиме `points`: за матч командам выставляются два произвольных целых числа (`pointsA`/`pointsB`). В round-based-форматах разворачивается в индивидуальные очки игроков (`PlayerMatchScore`). |
| **Матч** | Отдельная игровая встреча двух сторон с результатом и победителем. В playoff — узел турнирной сетки (`Match`); в round-based-форматах — матч раунда на корте (`RoundMatch`). |
| **Раунд** (`Round`) | В round-based-форматах — тур, в котором все участники одновременно играют свои матчи; контейнер набора матчей раунда. В playoff «раунд» (`Match.round`) — это уровень дерева сетки (1 — первый круг, последний — финал). |
| **Корт-матч** (`RoundMatch`) | Матч раунда, привязанный к корту (`courtNumber`), с двумя динамическими командами, заданными до четырёх ссылок на игроков (`teamA1`/`teamA2` против `teamB1`/`teamB2`). В одиночных форматах 1×1 заполняются только `teamA1`/`teamB1`; в парном round_robin слоты переиспользуются: `teamA1`+`teamA2` — одна пара, `teamB1`+`teamB2` — другая. |

### Пять уровней игры (`skillLevel`)

Значения хранятся латиницей; русские названия — отображаемые подписи интерфейса.

| Значение (`skillLevel`) | Русское название |
|-------------------------|------------------|
| `beginner` | новичок |
| `progressing` | прогрессирующий |
| `intermediate` | средний |
| `advanced` | высокий |
| `pro` | профессиональный |

## 2. Форматы турниров

Формат турнира (`format`) задаёт способ построения расписания/сетки и определения итога.
Поддерживаются четыре формата. Формат **ортогонален** режиму подсчёта (`scoringMode`).
Алгоритмы каждого формата подробно описаны в [форматах и алгоритмах](05-formaty-i-algoritmy.md).

| Формат (`format`) | Суть и отличия |
|-------------------|----------------|
| **Олимпийская** (`playoff`, single-elimination) | Турнир на вылет: проигравший выбывает, победитель проходит дальше по дереву сетки до финала; итог — пара-чемпион. Соревновательная единица — **пара** (партнёр фиксирован). Допускает только **4 / 8 / 16** участников (степень двойки, без bye-логики). Используется **посев** (`seed`); ничья не допускается — в playoff обязателен решающий счёт. |
| **Круговой** (`round_robin`) | Каждая единица играет с каждой ровно один раз; итог — по накопленной таблице (standings), без дерева. Единица — **пара ИЛИ одиночный игрок** (партнёр фиксирован). Свободное число участников (мягкий лимит 24). Ничья допустима. |
| **Американо** (`americano`) | Ротационный социально-соревновательный формат. Регистрация **одиночная**; партнёр **меняется каждый раунд по фиксированной схеме** (circle method на игроках — каждый сыграет в паре с каждым). Очки **индивидуальные**, итог — рейтинг игроков (не пара-чемпион). Всё расписание генерируется при старте (не зависит от результатов). Посев не применяется. |
| **Мексикано** (`mexicano`) | Как американо (одиночная регистрация, индивидуальные очки, итог-рейтинг), но пары и соперники **следующего** раунда формируются **динамически по текущему рейтингу** (самобалансирующийся). Расписание материализуется **раунд за раундом**: при старте — только раунд 1, далее каждый следующий раунд строится по результатам предыдущего. |

## 3. Подсчёт результатов

| Термин | Определение |
|--------|-------------|
| **Режим подсчёта** (`scoringMode`) | Настройка турнира, ортогональная формату: `sets` — счёт по сетам/геймам (теннисный стиль, детализация по сетам ведётся только в playoff); `points` — за матч командам выставляются два произвольных целых очка. Для американо/мексикано используется только `points`. |
| **Free-form (подсчёт без лимитов)** | Действующая модель подсчёта: **любое** число сетов, любые неотрицательные целые геймы за сет, очки — два произвольных целых, **без верхних лимитов и без правил win-by-2 / тай-брейк 7:6**. Победитель вычисляется по числу выигранных геймов/сетов (или по очкам). |
| **Ничья** (draw) | Равный результат сторон (равные сеты и сумма геймов, либо равные очки). **Допустима во всех форматах, кроме playoff.** В playoff ничья приводит к типизированной ошибке (`ResultError` с `code: "draw"`) и не вызывает продвижения — требуется решающий счёт. |
| **Победитель** (`winnerId`) | Вычисляемая сторона-победитель матча — источник истины для продвижения по сетке в playoff. В режиме `sets` — у кого больше выигранных сетов (тай-брейк — по сумме геймов); в `points` — у кого больше очков. |
| **Посев** (`seed`) | Порядковый номер пары (1..`size`), присваиваемый при генерации сетки playoff случайным перемешиванием (Fisher–Yates) и определяющий стартовые позиции в дереве. Применяется только в playoff. |
| **Рейтинг / турнирная таблица** (standings) | Производная (вычисляемая при каждом запросе, не материализуется) ранжировка участников. Для round_robin — таблица единиц (`kind: "units"`: победы в матчах → разница очков → …); для американо/мексикано — рейтинг игроков (`kind: "players"`: сумма личных очков → разница очков → победы → …). |
| **Тай-брейкер** | Вторичный критерий упорядочивания при равенстве основного показателя в standings (например, разница очков, число побед, стабильный фолбэк по идентификатору). Гарантирует **детерминированный** порядок — критично для мексикано, где таблица определяет состав следующего раунда. *(Не путать с тай-брейком гейма 7:6 — он в free-form не применяется.)* |
| **`targetPoints`** *(legacy)* | Поле модели `Tournament` — целевая сумма очков за матч в исходной (до free-form) модели подсчёта американо/мексикано. **Не используется**: после перехода на free-form убрано из формы создания и не читается; колонка осталась в БД (миграции не было). Аналогично де-факто не читаются `setsPerMatch` и `gamesPerSet`. |

## 4. Системные термины

| Термин | Определение |
|--------|-------------|
| **RSC** (React Server Component) | Серверный React-компонент: страница (`page.tsx`), выполняемая на сервере, читающая данные через сервис напрямую (без отдельного API-слоя и клиентского fetch) и отдающая готовый HTML. Все страницы чтения — RSC. |
| **Server Action** | Серверная функция с директивой `"use server"`, вызываемая прямо из формы для записи. «Тонкая»: guard (проверка доступа) → `parse*Form` (валидация) → вызов сервиса → `revalidatePath`. Возвращает `{ ok, fieldErrors?/error? }`, без redirect. Заменяет REST-эндпоинты для мутаций. |
| **Сервис** (service) | «Толстый» слой бизнес-логики в `src/lib/services/*.ts`: содержит правила домена и работу с Prisma, принимает экземпляр `prisma` параметром. Единственное место, где живёт логика форматов, подсчёта и переходов статусов. |
| **Валидация** (validation) | Проверка входных данных Zod-схемами в `src/lib/validation/*.ts`. Функции `parse*Form(formData)` — единый источник правды для клиентской формы и серверной границы (не могут разойтись). |
| **Guard** (страж доступа) | Функции авторизации в `src/lib/auth-guards.ts`: `getOptionalSession` (опциональная сессия), `requireUser` (требует входа, иначе редирект на login), `requireAdmin` (требует роль `admin`). Проверка доступа — на границе Server Action и в RSC, **не** в middleware. |
| **Сессия** (`Session`) | Аутентифицированный сеанс пользователя, управляемый Better Auth (cookie + запись в БД). Из сессии берутся идентичность и роль для guard-проверок. |
| **Роль** (`role`) | Уровень доступа пользователя: `player` (игрок — по умолчанию) или `admin` (администратор — единственный, создаётся seed-скриптом). Только `admin` создаёт турниры и вводит результаты. |
| **`revalidatePath`** | Функция Next.js для инвалидации серверного кэша маршрута после мутации, чтобы RSC-страница перерисовалась с новыми данными. Вызывается в конце каждого Server Action (заменяет real-time-обновления). |
| **Транзакция** (`prisma.$transaction`) | Атомарная группа операций с БД для целостности (например, запись пары с проверкой вместимости, перезапись результата). При ошибке — полный откат всех изменений группы. |
| **Типизированная ошибка** (code-дискриминант) | Доменная ошибка сервиса с полем `code` как дискриминантом (`ResultError`, `RegistrationError`, `AdminError`, `BracketError`, `FormatError`, `RoundResultError`). Наружу отдаётся только безопасное русское сообщение по `code`; сырой текст Prisma не раскрывается. |
| **ORM / Prisma** | Object-Relational Mapping — типобезопасный доступ к БД. Prisma (`@prisma/client`) генерирует типы из схемы, выполняет запросы и миграции. Экземпляр клиента — singleton в `src/lib/db.ts`. |
| **Миграция** (migration) | Версионированное изменение структуры БД, генерируемое и применяемое Prisma из `schema.prisma`. *(Free-form-изменение подсчёта проведено без миграции — затронутые колонки оставлены в БД с дефолтами.)* |
| **Seed** (сидирование) | Идемпотентный скрипт начального наполнения БД (`prisma/seed.ts`): создаёт администратора из переменных окружения (`ADMIN_EMAIL`/`ADMIN_PASSWORD`). Отдельный скрипт наполняет тестовых игроков. |

## 5. Сущности модели данных

Краткий справочник по девяти моделям. Полные поля, связи, ограничения и ER-диаграмма —
в документе [модель данных](04-model-dannyh.md).

**Аутентификация (генерируются Better Auth):**

| Модель | Назначение (кратко) |
|--------|---------------------|
| **`User`** | Игрок/администратор: идентичность (email, `nickname`), роль и доменные поля (`courtSide`, `skillLevel`, `phone?`, `birthDate?`). Пароля не хранит. |
| **`Session`** | Активный сеанс пользователя (токен, срок действия, привязка к `User`). |
| **`Account`** | Учётная запись провайдера входа; хранит пароль (`password`, scrypt) для email+password. |
| **`Verification`** | Служебные токены верификации Better Auth (email-верификация в проекте выключена). |

**Домен playoff / пары:**

| Модель | Назначение (кратко) |
|--------|---------------------|
| **`Tournament`** | Турнир: `format`, `participantMode`, `scoringMode`, `level`, `size`, `status`, опц. `date`/`location`/`price`. Корень всех связей. |
| **`Pair`** | Зарегистрированная пара в турнире (`player1`/`player2`, `seed?`). Соревновательная единица парных форматов. |
| **`Match`** | Узел дерева single-elimination: позиция в сетке, стороны, `winnerId`, указатель продвижения (`nextMatchId`/`nextSlot`). |
| **`SetScore`** | Один сет матча playoff: номер сета и геймы каждой стороны. |

**Домен round-based (round_robin / americano / mexicano):**

| Модель | Назначение (кратко) |
|--------|---------------------|
| **`TournamentPlayer`** | Одиночная регистрация игрока в турнире (связь `Tournament`↔`User`). |
| **`Round`** | Контейнер раунда round-based-формата (номер, `status`). |
| **`RoundMatch`** | Матч раунда на корте: две динамические команды (до 4 ссылок на игроков) и очки сторон (`pointsA`/`pointsB`). |
| **`PlayerMatchScore`** | Индивидуальные очки игрока в корт-матче (`pointsFor`/`pointsAgainst`, `teamSlot`) — основа рейтинга американо/мексикано. |
