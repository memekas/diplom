# Рисунок 7 — аудит блок-схемы по ГОСТ 19.701-90

Файл-источник: `07-algoritm-zapuska.drawio` (рендер: `07.png`).
Дата аудита: 2026-06-24. Повод: замечание науч. рук. —
«В б-с алгоритма д. б. один блок *Начало* (есть) и один блок *Конец*».

## Что сделано

Схема имела **1 «Начало» и 5 «Конец»** (успешный финал `endOk` + по одному
терминатору на каждую ветвь ошибки: нет прав / не регистрация / неверное
число / сетка уже создана). Замечание устранено: **оставлен один «Конец»**.

Все ветви (успешный путь + 4 ветви ошибок) сведены в единственный терминатор,
причём в «Конец» входит **ровно одна линия — СВЕРХУ** (п. 4.2.4):
- 4 ветви ошибок сливаются в общий ствол (x=880) **простыми линиями (T-стык)**
  без наконечников, со **смещёнными** местами слияния (п. 4.2.3). Притоки идут
  в стандартном направлении (слева-направо) — наконечник по п. 4.2.1 не требуется
  (он обязателен лишь для нестандартного направления); T-стык сам по себе
  однозначен (линия обрывается на стволе = связь, а не сквозное пересечение
  п. 4.2.2);
- ствол **вливается в линию успешного потока** (`p7→Конец`) ДО терминатора,
  и далее одна линия входит в «Конец» сверху; на повороте ствола справа-налево
  (R→L, нестандартное направление) наконечник **обязателен** (п. 4.2.1) — стоит;
- точки-узлы (junction dots) не ставим: по ГОСТ 19.701-90 необязательны
  (нормирована только смещённость, п. 4.2.3), а слияния — чистые T-стыки без
  сквозных пересечений;
- на горизонтальном (справа-налево) участке ствола стоит стрелка направления
  (п. 4.2.1).

Структурно проверено: 1 «Начало», 1 «Конец», единственный вход в «Конец» —
сверху (`p7`); входов в правую грань нет.

**Почему так, а не два входа / вход справа:** по п. 4.2.4 линии подходят к
символу только **слева или сверху** (справа/снизу — для исходящих). Вход в
«Конец» справа — нарушение. По п. 4.2.3 несколько линий объединяются в одну
до входа в символ (места объединения смещены). Поэтому ствол ошибок слит с
линией успеха в одну, и в терминатор идёт единственная стрелка сверху.

## Проверка нотации (символы — соответствуют ГОСТ 19.701-90)

| Символ | Применение в схеме | Норма |
|--------|--------------------|-------|
| Терминатор (скруглённый прямоуг./овал) | «Начало», «Конец» | ✓ п. 3.4.2 |
| Процесс (прямоугольник) | действия `p1`–`p7`, ветви ошибок `er1`–`er4` | ✓ |
| Решение (ромб) | проверки `d1`–`d4`, два помеченных выхода «да»/«нет» | ✓ |
| Линии потока | вход в символы слева/сверху, выход справа/снизу | ✓ п. 4.2.4 |
| Слияние линий | ствол ошибок + линия успеха → одна линия в «Конец»; узлы смещены | ✓ п. 4.2.3 |
| Стрелки | стандартное направление без стрелок; на R→L участке стрелка | ✓ п. 4.2.1 |

## Важный нюанс для защиты

**«Один Начало — один Конец» — это НЕ буква ГОСТ 19.701-90.** Сам стандарт
(= ИСО 5807-85) определяет только символ «Терминатор» (п. 3.4.2 — назначение:
«выход во внешнюю среду… начало или конец схемы») и **нигде не нормирует число
терминаторов**; слово «единственный» в тексте не встречается, а п. 4.3.1
(«Несколько выходов») вообще легализует множественные выходы.

Требование «один вход — один выход» происходит из **принципа структурного
программирования** (теорема Бёма–Якопини, 1966; Дейкстра/Миллс: single-entry/
single-exit) и из **требований нормоконтроля / вузовских методичек**.

➡️ На защите формулировать так: единственный «Конец» соблюдён **по
требованию нормоконтроля и принципу структурного программирования**, а не как
«прямая буква ГОСТ 19.701-90». Соблюдать — обязательно (нормоконтроль требует),
обосновывать — корректно.

## Что НЕ меняли (рассмотрено и отклонено)

Адверсариальная проверка двух дополнительных правок показала, что их применять
нельзя — они внесли бы новые ошибки:

1. **Перевод блоков чтения/вывода в параллелограмм «Данные» — отклонено.**
   `p5` («Создание матчей/раундов») — настоящая вычислительная операция
   (генератор Фишера–Йетса), это «Процесс». Ветви ошибок `er1`/`er4` — не
   ввод-вывод данных. Массовая замена на параллелограмм нарушила бы ГОСТ.
   Спорен только `p2` («Чтение формата из БД») — допустим как «Процесс»
   (действие «чтение»); при желании — символ хранимых данных/БД, **не** общий
   параллелограмм. Изменение необязательное, оставлено как есть.

2. **Перестановка проверок перед чтением/обработкой — отклонено.** ГОСТ
   19.701-90 — стандарт нотации, **порядок логики алгоритма не регламентирует**.
   Схема точно отражает код: `format-engine.ts startFormat` сначала читает
   `tournament.format` и выбирает генератор (`p2`/`p3` — чистые чтения без
   побочных эффектов), затем `bracket.ts generateBracket` в транзакции проверяет
   статус (`d2`) → число пар (`d3`) → отсутствие матчей (`d4`) и только потом
   делает жеребьёвку/создание (`p4`/`p5`). Первая мутация стоит **после** всех
   проверок — дефекта «обработка до валидации» нет. Перестановка рассинхронила
   бы схему с кодом.
