<objective>
Add the structured-scoring schema and the transactional advancement engine. Migrate the `SetScore` model (per-set games, cascade-delete from Match) plus the `Match.setsWonA/B` cached counts and the `Match.setScores` back-relation, then build `recordResult(prisma, matchId, sets[])` — ONE `$transaction` that loads the match + its tournament's `setsPerMatch`/`gamesPerSet`, validates every set via Plan 01's `setWinner`, derives the match winner via `matchWinnerFromSets`, persists the SetScores + cached counts + `winnerId`, advances the winner into the pre-existing parent slot, and finishes the tournament on the final. Built test-first against a fake prisma, exactly like `generateBracket`.

Purpose: This is the correctness heart of MATCH-02 (winner derived + advance in one transaction), MATCH-03 (final → finished + champion source), MATCH-04 (free edit: delete + re-derive + re-propagate), and MATCH-05 (structured SetScore storage; counts read from the Tournament fields, no migration of Tournament). Reusing Phase 4's already-wired `nextMatchId`/`nextSlot` means advancement is an UPDATE of the pre-existing parent slot — never a re-created match (Pitfall 1).
Output: migrated schema; `recordResult` in `src/lib/services/result.ts`; expanded `result.test.ts`.
</objective>

    SCHEMA (read prisma/schema.prisma first — Match already has winnerId/nextMatchId/nextSlot from Phase 4; Tournament already has setsPerMatch=3/gamesPerSet=6 from Phase 2 — do NOT re-add those):
    - Add `model SetScore { id String @id @default(cuid()) matchId String match Match @relation(fields: [matchId], references: [id], onDelete: Cascade) setNumber Int gamesPair1 Int gamesPair2 Int @@unique([matchId, setNumber]) @@map("set_score") }`.
    - Add to Match: `setsWonA Int?`, `setsWonB Int?` (cached display counts; winnerId stays the advancement source of truth), and the back-relation `setScores SetScore[]`.
    - Do NOT touch the kysely override, auth tables, Tournament.setsPerMatch/gamesPerSet, or Match's existing advancement fields.

    recordResult(prisma, matchId: string, sets: { gamesPair1: number; gamesPair2: number }[]) — ALL in one `prisma.$transaction(async (tx) => { ... })` (mirror generateBracket's tx structure; cast `tx as unknown as PrismaClient` when calling transitionTournament, as bracket.ts does):
      1. Load the match via `tx.match.findUniqueOrThrow` selecting id, tournamentId, pairAId, pairBId, nextMatchId, nextSlot, and the tournament's setsPerMatch + gamesPerSet (via `tournament: { select: { setsPerMatch: true, gamesPerSet: true } }`).
      2. Reject (throw ResultError "slots_unfilled", RU msg) if `pairAId` or `pairBId` is null — cannot record before opponents are decided (Pitfall 5, results-out-of-order).
      3. Reject (throw ResultError "empty", RU msg) if `sets` is empty, or if `sets.length > setsPerMatch`.
      4. For each set call `setWinner(gamesPair1, gamesPair2, gamesPerSet)` (re-throws ResultError "invalid_set" from Plan 01) and tally: setsWonA = count of sets won by side "A", setsWonB = side "B".
      5. Derive `winnerSide = matchWinnerFromSets(perSetWinners, setsPerMatch)`. If null → throw ResultError "no_winner" (RU msg: not enough decisive sets). winnerId = winnerSide === "A" ? match.pairAId : match.pairBId. Assert winnerId ∈ {pairAId, pairBId} (it is by construction — defensive).
      6. `tx.setScore.deleteMany({ where: { matchId } })` then create the new rows (setNumber = index+1, gamesPair1/gamesPair2 from input) — supports free editing (MATCH-04). Use createMany if available on the fake/real client, else a loop of create.
      7. `tx.match.update` this match: `{ setsWonA, setsWonB, winnerId }`.
      8. Advancement (MATCH-02): if `nextMatchId` is set, `tx.match.update({ where: { id: nextMatchId }, data: nextSlot === "A" ? { pairAId: winnerId } : { pairBId: winnerId } })` — an UPDATE into the pre-existing parent slot (Phase 4 wired it). On a re-record (MATCH-04) this simply overwrites the parent slot with the (possibly new) winner — re-propagation to the IMMEDIATE parent only; cascade cleanup of further-downstream matches is explicitly OUT OF SCOPE (accepted, per CONTEXT deferred).
      9. Final (MATCH-03): if `nextMatchId` is null, this is the final → call `transitionTournament(tx, match.tournamentId, "in_progress", "finished")`. NOTE: on a re-record of an already-final match, the tournament is already "finished" and transitionTournament will reject the stale `from` — guard by skipping the transition when the tournament is already finished (re-read status, or wrap that single call so an already-finished tournament is a no-op rather than a throw). Do NOT swallow other errors.
      Return a small summary (e.g. `{ matchId, winnerId, setsWonA, setsWonB, finished: boolean }`).

    TEST (extend result.test.ts using the bracket.test.ts fake-prisma pattern — a hand-written object whose `$transaction(fn)` invokes `fn(tx)` with the same fake; in-memory match/setScore/tournament records; async cases inside `main()` because tsx emits CJS):
    - Advance: a both-slots-filled non-final match, sets [{6,4},{6,3}] → winnerId = pairA, setsWonA 2 / setsWonB 0, parent match's slot (per nextSlot) updated to pairA's id; tournament NOT finished.
    - 2:1 path: sets [{6,4},{4,6},{7,5}] → winner pairA (2 sets), 3 SetScore rows persisted.
    - Final: a match with nextMatchId null, decisive sets → tournament transitioned to "finished"; no parent update.
    - Reject slots_unfilled: a match with pairBId null → throws ResultError "slots_unfilled"; NO setScore/ match write, NO parent write, NO status change.
    - Reject no_winner: sets [{6,4},{4,6}] (1:1, setsPerMatch 3) → throws ResultError "no_winner"; nothing persisted.
    - Reject invalid_set: sets [{6,5}] → throws ResultError "invalid_set" (bubbled from setWinner); nothing persisted.
    - Reject empty: sets [] → throws ResultError "empty".
    - Free edit (MATCH-04): record [{6,0},{6,0}] (winner A) then re-record [{0,6},{0,6}] (winner B) on the SAME match → old SetScores gone (exactly 2 rows, the new ones), winnerId now pairB, parent slot now holds pairB's id.
  </behavior>
