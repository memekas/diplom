<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser ↔ Better Auth route (`/api/auth/*`) | Untrusted credentials cross here; Better Auth validates + hashes (scrypt) |
| client form ↔ Server Component / session | Session derived from signed cookie only; client-supplied identity never trusted |
| npm registry ↔ local install | Third-party packages enter the build |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Information Disclosure | User reads crossing to client (dashboard/nav) | mitigate | Render only safe fields (name); never select/return password/Account rows (Pitfall 12); password is owned by Better Auth Account table, no passwordHash column exists |
| T-01-02 | Spoofing | Session identity | mitigate | Identity derived from `auth.api.getSession` (signed cookie) only; never from client props/form (Pitfall 8) |
| T-01-03 | Tampering | Registration input | mitigate | Zod `registerSchema` validates email/password/name/phone/skillLevel before signUp; Better Auth enforces password hashing |
| T-01-04 | Elevation of Privilege | role field at signup | mitigate | role defaults "player" server-side; not accepted from the register form; admin role only set by seed (plan 02) |
| T-01-SC | Tampering | npm installs (next, prisma@6, @prisma/client@6, better-auth, zod@4, tsx) | mitigate | All versions verified against npm registry on 2026-06-06 in STACK.md/AUTH.md Sources (HIGH); better-auth ~3.6M dl/wk, prisma/next/zod/tailwind first-party. No `## Package Legitimacy Audit` table in RESEARCH → treated as [ASSUMED]; packages are top-tier well-known with documented registry verification. Executor: confirm `npm install` reports no install-script warnings for unknown packages; pin prisma to 6.x (NOT 7). |
</threat_model>
