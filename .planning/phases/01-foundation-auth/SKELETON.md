# Walking Skeleton — Padel Tournaments

**Phase:** 1
**Generated:** 2026-06-06

## Capability Proven End-to-End

A new visitor registers (email, password, name) on the deployed-locally Next.js app, is auto-signed-in, and sees their own name on a dashboard page read from a live session — exercising scaffold → routing → Better Auth → one real SQLite write (signup) and one real read (session/dashboard) → an interactive UI control (logout). Runs via `npm run dev`.

> Note on the ROADMAP goal line: Phase 1's `**Goal:**` in ROADMAP.md is in prose, not "As a / I want to / so that" user-story form. The phase is inherently multi-actor (player + seeded admin). The skeleton capability above is the thinnest single-actor slice that proves the stack. If a strict single user-story framing is required, run `/gsd mvp-phase 1` to rewrite the ROADMAP goal — the plans here do not depend on that rewrite.

## Architectural Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Framework | Next.js 16 (App Router, TypeScript, `src/`) | Locked stack; Server Components for reads + Server Actions for writes, no separate API layer (STACK.md, ARCHITECTURE.md) |
| Package manager | **npm** | Universally available on grader machine, no extra install (CONTEXT.md decision; overrides STACK.md pnpm suggestion) |
| Data layer | Prisma **6.x (≥6.2, NOT 7)** + SQLite (`file:./dev.db`) | Simplest workflow (`prisma-client-js`, generates to node_modules); Prisma 7 driver-adapter complexity forbidden (STACK.md "What NOT to Use") |
| Prisma client | Global singleton in `src/lib/db.ts` (`export const prisma`) | Avoids dev hot-reload connection storm (STACK.md/PITFALLS Pitfall 9) |
| Auth | **Better Auth ^1.6** — prismaAdapter(sqlite) + emailAndPassword + `admin()` + `nextCookies()` | Maintained named library fitting the stack; owns password hashing (scrypt) + session signing; runs in Node (no Edge pain). AUTH.md OVERRIDES STACK.md's hand-rolled recommendation |
| Password storage | Better Auth `Account` table (scrypt) — **NO `passwordHash` column on User** | Credentials owned by the library; never returned to client (AUTH.md, ARCHITECTURE.md, Pitfall 12) |
| Email verification | **Disabled** (Better Auth default) | Offline demo, no SMTP (CONTEXT.md, REQUIREMENTS Out of Scope) |
| Auth tables | Generated by `npx @better-auth/cli generate` (User/Session/Account/Verification) | Don't hand-write Better Auth's schema; add domain fields onto generated User |
| Roles | Better Auth `admin()` plugin — `role` on User, default `"player"`, admin = `"admin"` | Single seeded admin; no admin self-registration (REQUIREMENTS Out of Scope) |
| Enums | `String` fields + Zod unions for role/courtSide/skillLevel (NOT native Prisma enums) | Simpler against the Better-Auth-generated schema (CONTEXT.md Claude's discretion; ARCHITECTURE.md allows both) |
| Validation | Zod 4 (`src/lib/validation/*.ts`) | Validate form input client-side + at the Server Action boundary |
| Authorization boundary | `requireUser()` / `requireAdmin()` in `src/lib/auth-guards.ts` over `auth.api.getSession({ headers })` | The REAL security boundary — called as the first line of every mutation; UI hiding is cosmetic (PITFALLS Pitfall 8, ARCHITECTURE) |
| Mutation pattern | Server Action: guard → Zod validate → service → `revalidatePath` | Thin actions over a fat, testable service layer (ARCHITECTURE Pattern 3) |
| Domain logic | `src/lib/services/*.ts` (plain async fns taking `prisma`) | Framework-agnostic, unit-testable (ARCHITECTURE) |
| Directory layout | `src/app/(auth)/*` (login/register), `src/app/(app)/*` (dashboard/profile/admin), `src/lib/{db,auth,auth-client,auth-guards,services,validation}`, `prisma/{schema.prisma,seed.ts}` | Route groups by audience; co-located actions per route group |
| UI | Tailwind 4 (CSS-first `@import "tailwindcss";`), plain JSX, no component kit | Locked; minimal forms (STACK.md) |
| Run target | Local `npm run dev` (full-stack exercised); SQLite file committed-ignored | Thesis demo, no deployment target needed (CONTEXT.md offline demo) |

## Out of Scope (Deferred to Later Slices)

- Tournaments, pairs, bracket, matches, scoring — Phases 2–5 (User is the only model needed in Phase 1; Tournament/Pair/Match/SetScore are created in their own phases per ARCHITECTURE/ROADMAP schema notes)
- PLAYER-02 (court side shown in participant lists) — Phase 3, alongside the participant list
- Email verification, password reset — out of scope (no SMTP)
- Multi-admin / admin self-registration — out of scope (single seeded admin)
- Native Prisma enums, middleware-based auth — deliberately avoided (String + zod; guards are the boundary, not middleware)
- Court-side auto-pairing / ranking logic — display-only in v1 (RANK-01 is v2)

## Subsequent Slice Plan

Each later phase adds one vertical slice on top of this skeleton without altering its architectural decisions:

- **Phase 2 — Tournaments & Status Machine:** admin creates a tournament (size 4/8/16); everyone sees the list + status page; server-guarded status transitions. Adds `Tournament` model (with `setsPerMatch`/`gamesPerSet` defaults) reusing `requireAdmin`.
- **Phase 3 — Registration & Pairs:** player picks a partner (Variant B) → `Pair`; atomic integrity + capacity lock; participant list shows court side (PLAYER-02). Reuses `requireUser`, service+action pattern.
- **Phase 4 — Bracket Generation & Public View:** admin "Start" → Fisher–Yates draw into an immutable match tree; public bracket view (Core Value). Reuses `requireAdmin`, transactions.
- **Phase 5 — Results & Advancement:** admin enters per-set scores → derived set/match winner → transactional auto-advancement → champion. Adds `SetScore`; reuses guards + revalidate pattern.
