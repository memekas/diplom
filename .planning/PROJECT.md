# Padel Tournaments

## What This Is

Веб-приложение для организации турниров по паделу. Падел — командный спорт: за одну команду играют два игрока (пара). Платформа делается для одной конкретной организации, которая выступает администратором: только она создаёт турниры. Игроки регистрируются, участвуют парами, смотрят информацию о турнире и турнирную сетку.

Дипломная работа — не продакшн, реальной нагрузки не будет. Приоритет: простое работающее приложение, сделанное быстро, без усложнений и преждевременной оптимизации.

## Core Value

Организация может создать playoff-турнир для пар, игроки регистрируются в него парами, и все могут видеть турнирную сетку с результатами по мере продвижения.

## Current Milestone: v2.0 — Мультиформатные турниры + полный UX

**Goal:** Расширить движок с единственного playoff-для-пар до четырёх форматов (playoff / round-robin / американо / мексикано) с одиночной и парной записью, матчингом по уровню и настраиваемым режимом подсчёта (сеты-геймы или просто очки, без лимитов), и довести UX до бизнес-требований (только русский, тёмная тема, адаптив, главная со списком открытых турниров, шапка с ЛК, расширенный личный кабинет).

**Target features:**
- 4 формата турниров: Олимпийская (playoff, есть), Раунд-робин, Американо, Мексикано (ротационные, индивидуальные очки)
- Одиночные и парные турниры; американо/мексикано — только одиночные (система ротирует пары)
- Матчинг по уровню при регистрации (строгое равенство 5 RU-уровней)
- Настраиваемый режим подсчёта на турнир: сеты/геймы (без лимита числа сетов и геймов) или просто очки (любые целые)
- Поля турнира: формат, одиночный/парный, уровень, количество, цена (оплата в клубе)
- Админ: удаление зарегистрированных, ручное завершение турнира
- Полный UX: RU-локализация, тёмная тема, адаптив, главная (открытые турниры), шапка (клуб/логотип/прошедшие/ЛК), расширенный ЛК (правка всех полей включая email/ник)

**Phase structure:** горизонтальные слои — Фаза 7 (модель данных) → Фаза 8+ (бэкенд) → Фаза 10+ (фронтенд/UX). Порядок слоёв строгий.

### Out of Scope

- Жеребьёвка с bye для не-степени-двойки — playoff остаётся ровно 4/8/16 (round-robin/американо/мексикано — свободное число участников)
- Групповой этап и double elimination — не входят в набор форматов v2.0
- Очки внутри гейма (15/30/40, golden point, advantage) — режим `points` считает произвольные целые на матч, не теннисные внутригеймовые очки
- Глобальные рейтинги игроков между турнирами — есть только standings внутри турнира (американо/мексикано)
- Онлайн-оплата — цена отображается, оплата в клубе (п.3.4.7)
- Real-time через websockets — обновление через `revalidatePath` после действий админа
- Push/email-уведомления — вне рамок дипломной работы
- Мобильное приложение — только адаптивный веб
- Высоконагруженная оптимизация, кэширование, масштабирование — не требуется (диплом, нет реальной нагрузки)

## Context

- Дипломная работа. Не будет использоваться в реальной жизни. Цель — рабочая демонстрация, не продакшн-система.
- Заказчик — одна конкретная организация, проводящая турниры. Она же единственный администратор платформы.
- Падел как предметная область важен в основном для оформления; ключевая механика — пары (2 игрока) и playoff-сетка.
- Главный принцип: простота и скорость разработки важнее оптимальности и расширяемости.

## Constraints

- **Tech stack**: Next.js 16 (TypeScript, App Router) full-stack — Server Components (чтение) + Server Actions (запись), Prisma 6.x (≥6.2), SQLite — Один язык и один репозиторий, быстрый старт, удобный рендер сетки на фронте; выбрано в questioning
- **Auth-библиотека**: Better Auth `^1.6` (email+password, `admin()` plugin для роли, Prisma-адаптер, SQLite, Node runtime) — Живая поддерживаемая библиотека (research/AUTH.md); email-верификация выключена для офлайн-демо
- **Bracket**: только 4 / 8 / 16 пар (степень двойки) — Упрощает генерацию сетки, исключает bye-логику
- **Scoring**: структурный теннисный счёт — матч = сеты, сет = геймы; `Tournament.setsPerMatch` (v1=3) и `gamesPerSet` (v1=6) хранятся полями, в v1 фиксированы дефолтами, настройка через UI — v2 — Заложена будущая настраиваемость без миграции; победитель сета/матча вычисляется (win-by-2 / 7:6)
- **Auth**: единственный админ — предзаданный seed-аккаунт с ролью `admin` (создаётся идемпотентно из env) — Организация одна, регистрация админов не нужна
- **Scope**: дипломная работа — Делать просто и быстро, без преждевременной оптимизации и лишних фич

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Стек Next.js 16 full-stack (TS, App Router, Prisma 6, SQLite) | Один язык/репозиторий, быстрый старт, сетка на фронте | ✓ Good (v1.0) |
| Аутентификация — Better Auth `^1.6` (не hand-roll, не Auth.js v5) | Живая поддерживаемая библиотека, email+password + admin-роль из коробки, Node-native | ✓ Good (v1.0) |
| Админ = seed-аккаунт + роль `admin` (идемпотентный seed из env) | Организация — единственный админ, регистрация админов не нужна | ✓ Good (v1.0) |
| Playoff только для 4/8/16 пар | Упрощает генерацию сетки, без bye-логики | ✓ Good (v1.0) |
| Партнёр — выбор из зарегистрированных пользователей (Variant B) | Целостность данных, без флоу приглашений/подтверждений | ✓ Good (v1.0) |
| Сетка генерируется по кнопке «Старт» админом (random Fisher–Yates) | Явный контроль момента старта, регистрация закрывается при 4/8/16 парах | ✓ Good (v1.0) |
| Структурный счёт: матч = сеты → геймы (как в теннисе); `setsPerMatch`/`gamesPerSet` — поля БД, v1 фикс 3/6 | Пользователь требует счёт по сетам и геймам; заложена будущая настраиваемость без миграции | ✓ Good (v1.0) |
| Победитель сета/матча вычисляется (win-by-2 или тай-брейк 7:6; матч = 2 сета из 3) | Источник истины продвижения — вычисленный `winnerId`; очки внутри гейма не ведём | ✓ Good (v1.0) |
| Результаты вводит админ (по сетам), победитель авто-продвигается; правка свободная (delete+reinsert SetScores) | Централизованный контроль, минимум ограничений — проще для диплома | ✓ Good (v1.0) |
| Singles-турниры со случайным подбором — в v2 | Сначала простейший рабочий формат (playoff для пар) | ✓ Good (v1.0) |
| Никнейм — обязательное `@@unique` поле User через Better Auth `additionalFields`; дубль ловится по `error.code` FAILED_TO_CREATE_USER (signUp атомарен) | Стабильный человекочитаемый идентификатор; уникальность на уровне БД, без отдельной проверки-перед-вставкой | ✓ Good (v1.1) |
| Запись партнёра вводом ника (точный, регистрозависимый lookup) вместо select; резолв в userId ДО транзакционного registerPair | Убирает раскрытие списка юзеров, сохраняет v1.0 целостность пар нетронутой | ✓ Good (v1.1) |
| Американо/мексикано — одиночная регистрация + системная ротация пар по раундам, индивидуальные очки, итог = рейтинг игроков (не пара-чемпион) | Канонические правила форматов; парная-по-нику остаётся только для playoff и round-robin | ⏳ v2.0 |
| Матчинг уровня при регистрации — строгое равенство уровня игрока и турнира (5 RU-уровней) | Дословно по бизнес-требованию п.3.5; нельзя на турнир не своего уровня | ⏳ v2.0 |
| Playoff остаётся 4/8/16 (без bye); round-robin/американо/мексикано — свободное число участников | Сохраняет простую генерацию сетки без bye-логики; ограничение размера format-зависимое | ⏳ v2.0 |
| ЛК правит все поля профиля, включая email (флоу смены email Better Auth) и ник (с проверкой уникальности) | Бизнес-требование п.2.3 «править данные из 2.1»; id-поля меняются через защищённые пути | ⏳ v2.0 |
| Режим подсчёта — настройка турнира (`scoringMode`: сеты-геймы \| просто очки), ортогонален формату; без верхнего лимита на число сетов/геймов/очков | Пользователь требует оба режима и любой формат × любой режим; снимает v1-фиксацию 3/6 | ⏳ v2.0 |
| Завершение турнира — ручное действие админа (для всех форматов); у round-robin/американо/мексикано «финала» нет | Бизнес-требование п.3.6.4; авто-финиш playoff на финале дополняется явной кнопкой | ⏳ v2.0 |
