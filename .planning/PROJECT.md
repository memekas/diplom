# Padel Tournaments

## What This Is

Веб-приложение для организации турниров по паделу. Падел — командный спорт: за одну команду играют два игрока (пара). Платформа делается для одной конкретной организации, которая выступает администратором: только она создаёт турниры. Игроки регистрируются, участвуют парами, смотрят информацию о турнире и турнирную сетку.

Дипломная работа — не продакшн, реальной нагрузки не будет. Приоритет: простое работающее приложение, сделанное быстро, без усложнений и преждевременной оптимизации.

## Core Value

Организация может создать playoff-турнир для пар, игроки регистрируются в него парами, и все могут видеть турнирную сетку с результатами по мере продвижения.

## Current Milestone: v1.1 Никнеймы и запись по нику

**Goal:** У каждого игрока есть уникальный никнейм; запись на турнир — по нику партнёра, а не выбором из списка.

**Target features:**
- Поле `nickname` у пользователя, задаётся при регистрации, уникальное (гарантия на уровне БД + проверка при регистрации)
- Форма участия в турнире: выбор партнёра вводом никнейма с точным lookup вместо select-списка

### Out of Scope

- Турниры для одиночек со случайным подбором пары — отложено в v2 (сначала простой playoff для пар)
- Другие форматы (round-robin, групповой этап, double elimination) — v2
- Жеребьёвка с bye для не-степени-двойки — не нужно, регистрация закрывается ровно на 4/8/16 парах
- Очки внутри гейма (15/30/40, golden point, advantage) и супер-тай-брейк в решающем сете — счёт ведётся по геймам в сете, не по очкам
- UI для настройки числа сетов/геймов на турнир — v2 (поля `setsPerMatch`/`gamesPerSet` в БД уже есть, в v1 используются дефолты)
- Оплата, рейтинги игроков, push/email-уведомления — вне рамок дипломной работы
- Мобильное приложение — только веб
- Высоконагруженная оптимизация, кэширование, масштабирование — не требуется (диплом, нет реальной нагрузки)

## Context

- Дипломная работа. Не будет использоваться в реальной жизни. Цель — рабочая демонстрация, не продакшн-система.
- Заказчик — одна конкретная организация, проводящая турниры. Она же единственный администратор платформы.
- Падел как предметная область важен в основном для оформления; ключевая механика — пары (2 игрока) и playoff-сетка.
- Главный принцип: простота и скорость разработки важнее оптимальности и расширяемости.

## Constraints

- **Tech stack**: Next.js 16 (TypeScript, App Router) full-stack — Server Components (чтение) + Server Actions (запись), Prisma 6.x (≥6.2), SQLite — Один язык и один репозиторий, быстрый старт, удобный рендер сетки на фронте; выбрано в questioning
- **Auth-библиотека**: Better Auth `^1.6` (email+password, `admin()` plugin для роли, Prisma-адаптер, SQLite, Node runtime) — Живая поддерживаемая библиотека (research/AUTH.md); email-верификация выключена для офлайн-демо
- **Bracket**: только 4 / 8 / 16 пар (степень двойки) — Упрощает генерацию сетки, исключает bye-логику
- **Scoring**: структурный теннисный счёт — матч = сеты, сет = геймы; `Tournament.setsPerMatch` (v1=3) и `gamesPerSet` (v1=6) хранятся полями, в v1 фиксированы дефолтами, настройка через UI — v2 — Заложена будущая настраиваемость без миграции; победитель сета/матча вычисляется (win-by-2 / 7:6)
- **Auth**: единственный админ — предзаданный seed-аккаунт с ролью `admin` (создаётся идемпотентно из env) — Организация одна, регистрация админов не нужна
- **Scope**: дипломная работа — Делать просто и быстро, без преждевременной оптимизации и лишних фич

## Key Decisions

| Decision | Rationale | Outcome |
|----------|-----------|---------|
| Стек Next.js 16 full-stack (TS, App Router, Prisma 6, SQLite) | Один язык/репозиторий, быстрый старт, сетка на фронте | ✓ Good (v1.0) |
| Аутентификация — Better Auth `^1.6` (не hand-roll, не Auth.js v5) | Живая поддерживаемая библиотека, email+password + admin-роль из коробки, Node-native | ✓ Good (v1.0) |
| Админ = seed-аккаунт + роль `admin` (идемпотентный seed из env) | Организация — единственный админ, регистрация админов не нужна | ✓ Good (v1.0) |
| Playoff только для 4/8/16 пар | Упрощает генерацию сетки, без bye-логики | ✓ Good (v1.0) |
| Партнёр — выбор из зарегистрированных пользователей (Variant B) | Целостность данных, без флоу приглашений/подтверждений | ✓ Good (v1.0) |
| Сетка генерируется по кнопке «Старт» админом (random Fisher–Yates) | Явный контроль момента старта, регистрация закрывается при 4/8/16 парах | ✓ Good (v1.0) |
| Структурный счёт: матч = сеты → геймы (как в теннисе); `setsPerMatch`/`gamesPerSet` — поля БД, v1 фикс 3/6 | Пользователь требует счёт по сетам и геймам; заложена будущая настраиваемость без миграции | ✓ Good (v1.0) |
| Победитель сета/матча вычисляется (win-by-2 или тай-брейк 7:6; матч = 2 сета из 3) | Источник истины продвижения — вычисленный `winnerId`; очки внутри гейма не ведём | ✓ Good (v1.0) |
| Результаты вводит админ (по сетам), победитель авто-продвигается; правка свободная (delete+reinsert SetScores) | Централизованный контроль, минимум ограничений — проще для диплома | ✓ Good (v1.0) |
| Singles-турниры со случайным подбором — в v2 | Сначала простейший рабочий формат (playoff для пар) | ✓ Good (v1.0) |
